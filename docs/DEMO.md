# 演示与技术讲解提示

## 三分钟演示

1. `npm ci`、`npm run build`、`npm start`，打开 http://127.0.0.1:3000。
2. 解释总资产 10 万元为何包含 2 万元现金，指出 A01 40%、科技 60% 的两项提醒。
3. 卖 A01 100 股，指出现金变为 3 万元，30% / 50% 等于阈值，因此不提醒。
4. 买 A02 100 股，指出连续操作后现金 2.5 万元、A02 500 股、科技 55%，行业再次超限。
5. 输入不合法数量，或尝试买超出余额的数量，解释后端拒绝且上次有效结果保持不变。
6. 命名并保存，刷新页面、到方案列表重开；停止服务再启动后重开一次。
7. 新建模拟，展示原始持仓与现金仍未改变。

## 应能解释的六个问题

**为什么用整数分？** 直接用浮点元计算可能出现十进制误差；后端先严格解析为整数分并检查安全范围，展示时再转回字符串。

**为什么不是用显示百分比判断超限？** 显示会四舍五入，30.004% 可能显示 30.00%。判定用 BigInt 交叉相乘，独立于展示。

**如何保证失败操作不影响已有模拟？** 后端从原始组合拷贝后重放整个操作列表，失败直接拒绝；前端只在完整成功后更新当前操作与结果。

**为什么保存快照和操作？** 既能复算又能解释过程；只存当前文件引用，未来改价格可能导致已保存方案漂移；只存结果不便核对计算来源。

**为什么需要后端？** 即使绕过页面直接发请求，余额、持仓、数量和阈值仍必须一致校验，保存不能信任客户端伪造的金额。

**AI 做了什么，你如何检查？** 据实说明使用 Codex 生成方案、代码、测试和文档；打开 VERIFY.md，展示题目数字断言、真实 SQLite 重开、断网问题的红灯/修复及截图。提交前请自己至少完整演示一遍，确认能解释采用的设计。

## 关键代码入口

- `server/domain.ts`：整数分、占比和顺序模拟。
- `server/app.ts`：五个接口与错误结构。
- `server/store.ts`：快照与操作持久化。
- `client/App.tsx`：有效结果更新、保存、只读重开与未保存提示。
- `tests/domain.test.ts`、`tests/api.test.ts`：题目用例和精度/持久化核验。

## 大家都使用 AI 时，如何体现自己的能力

主线建议：把这个小项目讲成一次完整的前后端设计与验证，而不是逐个报框架名称。下面是可用的讲解结构，先实际操作并理解，再用自己的话表达。

| 可以重点讲的内容 | 具体说明 | 现场证据 |
|---|---|---|
| 前端状态的边界 | 草稿、请求中、有效结果、保存成功和重开只读是不同状态；只有服务端完整成功才替换有效结果 | 模拟一个断网或余额不足请求，观察已有两笔操作和现金数值保持不变 |
| 后端的信任边界 | 页面输入校验提升体验，API 仍独立拒绝非法数量、超额买卖和伪造结果 | 在网络面板看 422 错误，或运行对应 HTTP 测试，指出 operationIndex 和错误原因 |
| 持久化的设计取舍 | SQLite 保存快照与操作，派生结果重新计算，能够解释历史方案的来源 | 保存 AC-03、停止服务再启动、重开并核对现金 25000 与科技 55% |
| 财务口径的精确性 | 整数分处理金额，BigInt 判断严格大于阈值，展示舍入与判断独立 | 解释 30% 不提醒而 30.004% 虽显示 30.00% 仍提醒；指出专门测试 |
| 视觉设计的目的 | 用户选择纯白＋蓝色；减少渐变、阴影和重复卡片，放大重要数据，对发生变化的持仓作轻量标记 | 用同一操作前后的界面解释为什么这两行变蓝，颜色与状态都对应真实数据 |

一个可改写的开场：

> 这个项目采用 React 和 TypeScript 处理交互，Express 负责计算与校验，SQLite 保存方案。我重点考虑了买卖失败时怎样保留上次有效结果，以及重开历史方案时怎样保持行情快照一致。接下来用两笔交易和一次失败请求演示这些选择。

面试时按“做了什么 → 为什么这样做 → 备选方案 → 怎么验证”讲一项你真正理解的决策。比如保存最终结果更省事，但保存快照与操作更容易复算与解释；选择它也付出了冗余少量数据的代价。

个人贡献需要真实：明确哪些内容由 AI 生成，哪些是你复查后采纳、修改或否定的。当前代码与核验主要由 AI 辅助会话完成；可以先自己复现一个边界问题、沿调用链读懂并亲手完成一次小修改，再记录你的判断。这样讲解时有自己的依据，也更能回答追问。
